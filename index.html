Drivra's next product needs the platform underneath it to be honest first.

Drivra Mobility runs three live products — Upahar (driver rewards), Express (B2B delivery), and a GPS fleet dashboard — plus a marketing site and an ad hoc analytics tool, built up over roughly a year by a small team across two GitHub organizations. This document was triggered by a new product idea — rent-to-own motorcycle financing for drivers — but answering "what does that software look like" honestly required first answering "what does everything we've already built actually look like, and is it ready to carry a fintech product on top of it." Both answers are here.

The portfolio today

Four codebases, two GitHub orgs, one Supabase project doing more than it should

Everything below was confirmed by reading the actual repositories, not inferred from documentation.

Live · husig-ai/yapigo

Drivra Upahar

Rewards/loyalty layer for Yango moto-taxi drivers in Nepal. FastAPI + SQLAlchemy + Supabase Postgres. 1,793 drivers on the roster, 14.6% active in the last 30 days. Points economy, tiers, quests, badges, leaderboard. Reads Yango's Fleet API on a 15-minute sync; never writes back.

Live · husig-ai/drivra_express_backend

Drivra Express

B2B delivery platform for Kathmandu. FastAPI + SQLAlchemy, its own self-hosted Postgres (separate from Upahar's Supabase project). Drivers, merchants, hubs, orders, wallet, its own independently-built gamification system. Early-stage: 22 commits, no test suite yet.

Live · Drivra-Mobility/gps

GPS Dashboard

Fleet telematics — live map, idle/parked detection, misuse detection (GPS movement vs. Yango ride records). Vanilla JS, no backend of its own: reads and writes directly into Upahar's Supabase project via a client-side anon key and RLS. Fed by an external Lambda ETL.

New · this document

Rent-to-Own Financing

The product that started this exercise: let a driver finance their motorcycle through Drivra, with an internal credit signal built from their Upahar (and potentially Express) activity history. Proposed as a genuinely standalone service — see the full design.

The headline finding

Two of these four systems already share a database in a way that's caused a real production incident (a Supabase egress-quota breach) and a documented security gap (unrestricted table access before RLS was added). A new fintech product holding KYC documents and loan ledgers should not be built inside — or adjacent to — that pattern without fixing it first. See Architecture for the specific findings and the consolidation plan.

Method

This isn't a speculative strategy memo. The product-portfolio and architecture sections come from directly reading the five relevant repositories (yapigo, drivra_express_backend, gps_dashboard, drivra, drivra-web) — their models, migrations, deployment configs, and their own READMEs. The rent-to-own design draws on that same codebase reading plus external research: competitor products (RYD Nepal, M-KOPA, Tugende, Watu, Moove), Nepal's lending and KYC regulation (NRB/BAFIA), Nepal's payment rail landscape (eSewa, Khalti, Fonepay, ConnectIPS), and rough cost/infra benchmarking. Where a number is a genuine estimate rather than a confirmed fact, it's labeled as one.
