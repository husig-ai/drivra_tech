One sequence, not four separate projects

Phase 0: not engineering, parallel, starts now

  • Resolve the legal structuring path (Path A/B/C, see Regulation) with Nepali financial-regulatory counsel.
  • Direct competitive diligence on RYD Nepal: pricing verification, actual legal structure, fleet size, real default handling.
  • Start conversations with a potential licensed-lender partner if pursuing Path A (Hulas Finserv or comparable Class C/D institution).
  • Decide the GitHub org/governance question (husig-ai vs. Drivra-Mobility split) before a fifth product adds to the fragmentation.

Phase 1: harden & consolidate

This is the "low-hanging fruit" column from Architecture, done before or alongside the start of financing engineering: cheap, and it removes the specific risks a fintech product would otherwise inherit.

Phase 2: the identity layer & MVP financing

Platform

  • Build the canonical driver-identity layer (see Architecture)
  • Retire GPS Dashboard's direct anon-key table access in favor of a proper read API
  • Migrate Express's database to a managed service (RDS or its own Supabase project)

Financing MVP: human-in-the-loop

  • Driver/KYC data model, document upload, DIY Textract/Rekognition-assisted but human-approved verification
  • Manual underwriting review (no automated scorecard yet)
  • Basic servicing ledger, admin portal, SMS reminders
  • ConnectIPS/Fonepay-first manual payment reconciliation, field-agent cash collection tool

Goal: a small pilot cohort of 10 to 20 drivers, fully human-verified before automating anything, the same path Tugende and M-KOPA reportedly took before automating. This pilot scale is what the first-6-months cost estimate below is actually sized for.

Phase 3: automate what Phase 2 proved

  • Rules-based scorecard wired to the identity layer's Upahar (and Express, if live) performance data
  • Guarantor workflow for cold-start applicants
  • ConnectIPS mandate automation, delinquency dashboard, formal lien-registration workflow tracking
  • Express's partner API layer: auth, per-partner rate limiting, signed webhooks, idempotency, OpenAPI docs
  • Point-to-point delivery as a distinct Express order type
  • Cross-product analytics/data-warehouse layer live, fed on a schedule from each product's database

Phase 4: scale

  • Behavioral credit scoring from the financing service's own accumulated repayment data
  • Driver self-service native app (folded into Upahar or standalone)
  • Evaluate telematics/asset-monitoring for financed vehicles, reusing GPS Dashboard's existing pipeline, only if the reputational/hardware trade-off is judged worth it
  • Consolidate the two independently-built gamification systems (Upahar, Express) if that's still a strategic goal

Team & timeline for Phase 2 (financing MVP)

3 to 5 people: one senior backend engineer owning the lending/fintech domain, one additional backend engineer for KYC/payment integrations (reusing Upahar's Supabase/FastAPI patterns directly cuts this down from generic industry estimates), one mobile/frontend engineer (lighter load if reusing the Upahar app shell for the driver entry point), part-time product/compliance-ops (the NRB KYC/AML workstream is real work, not overhead), part-time QA/DevOps. Roughly 4 to 7 months to a v1, narrower than generic 8 to 10 month industry estimates because of pattern reuse and a deliberately narrow scope. Phase 1 hardening work is comparatively small, days to low weeks of existing-team time, not a separate budget line.

Open questions for the business

  1. Whether a licensed hire-purchase company specifically gets BAFIA §57's fast repossession rights, as opposed to a full BAFIA Class C finance company. Sources conflict, and this cannot be resolved by more research. Needs a Nepali banking/finance lawyer's direct read of Drivra's actual proposed structure. See Regulation.
  2. Legal structuring path: gates down-payment minimums, repossession rights, and go-to-market timeline.
  3. Capital source / lending partner: already in view, or does this design need to inform partner outreach?
  4. Vehicle sourcing: bulk dealer/brand relationship, or drivers bring their own vehicle for refinancing?
  5. Target down payment/tenure economics: Path A likely forces at least 40% down under NRB's LTV cap, Path B could go much lower.
  6. Positioning vs. RYD Nepal specifically: displace them, differentiate on trust/UX/loyalty-tier terms, or room for both.
  7. GitHub org/governance consolidation: resolve before a fifth product adds to the current two-org split.
